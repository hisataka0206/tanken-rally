# [[キャラ自動生成]] 仕様書（テクタン 次期大型アップデート）

> 2026-07-12 起案 / 対象アプリ: [[テクタン]]（旧 たんけんラリー）
> 生成モデル: [[NanoBanana Pro]]（[[Gemini 3 Pro Image]]）
> ステータス: 設計フェーズ（数値しきい値・taxonomy 具体化は「要決定」を参照）

---

## 1. 概要・狙い

固定素材のARキャラ（10種×6すがた）を超え、**探検の成果からその子だけのオリジナルキャラを AI が自動生成**し、[[図鑑]]コンプの底を無限に広げる。さらに生成キャラは**路線の[[共有キャラ]]**として他ユーザーの探検にも出現し、「がんばって歩く＝自分のキャラが世界に広がる」という強い動機を作る。

体験の核（確定済み）:

- **作成条件**: 一定のスコア以上 **かつ** 実際にたんけんをしたこと（移動せず適当に写真を撮っただけでは作れない）。
- **生成方法**: [[NanoBanana Pro]] を使用。
- **生成プロンプト**: ブランディング維持プロンプト＋駅名＋通ったスポット名＋距離に応じた要素＋ユーザーが選んだ変数。
- **作成ステップ**: 同一プロンプトで3体生成し、**灰色の影だけ**を見せる → ユーザーが1体選ぶ → 選んだ1体だけがカラーで登場、残り2体は棄却。
- **ユーザー変数**: 生き物デザインの**汎用記述語彙メニュー**から選ぶ（自由入力はしない）。男女問わず好みの見た目を出せる自由度を持たせる。
- **距離**: レア度に反映。**距離が長いほど他ユーザーのプレイに出やすくなる**。
- **命名**: 候補から選ぶ。
- **乱造方針**: 探検ごとに1体（条件を満たすたびに新規生成）。

## 2. 作成条件（ゲート ＝ 「本当にたんけんした」の証明）

「移動せず適当に写真を撮っただけ」を弾くため、**スコア条件**と**実探検の証明**を AND で課す。既存のスコア計算・EXIF・GPS・AR の信号を再利用する。

### 2-1. スコア条件
- [[実行点]]（実際に歩いた由来の得点）が **しきい値以上**（数値は要決定）。計画点ではなく実行点で判定するのが要点（ルートを作っただけでは出さない）。

### 2-2. 実探検の証明（アンチチート、複数条件の合成）
以下を合成して満たすことを要求（各しきい値は要決定）:

- **訪問スポット数**: 写真付きで訪れたスポットが **N 箇所以上**。
- **実移動の裏取り**: [[AR捕獲]]/スポット写真が **2箇所以上の異なる位置**（[[GPS]]座標）で発生している。
- **時間の広がり**: 写真の [[EXIF]] 撮影時刻が **M 分以上**にわたって分布（一瞬で連写だけ、を弾く）。
- **移動時間の一致度**: 既存スコア要素「[[Google移動時間との一致度]]」が一定以上（滞在時間を除いた純移動が現実的）。

> 設計方針: 単一指標は誤判定・不正双方に弱いので、**3つ以上の弱い条件の合成**で「本当に歩いた」を担保する。既存の `calculateScore()` の breakdown をそのまま流用する。

## 3. 生成方法（[[NanoBanana Pro]] の使い方）

調査で確認した [[Gemini 3 Pro Image]] の特性を前提に設計する。

- **画風固定 = 参照画像**: 最大14枚の参照画像を役割指定付きで渡せる（最初の6枚が高忠実度）。**既存キャラのアートシート3〜6枚を「スタイル参照」**として渡し、線・配色・頭身・目の大きさ・シール的な質感をブランドに固定する。
- **3体候補 = 1リクエストで最大4枚生成**。3体を1回で取得できる（コスト・レイテンシに有利）。
- **安全フィルタ**: プロンプト側の安全設定に加え、サーバ側の **IMAGE_SAFETY**（無効化不可）が生成画像を走査。子供向けにとって望ましい（誤って無効化できない）。`finishReason: "IMAGE_SAFETY"` を必ずハンドリングする（§10・§12）。
- **[[SynthID]]**: 生成画像には不可視の電子透かしが常時埋め込まれる（AI生成物の来歴担保として、共有機能の信頼性に活用可能）。
- **テキスト描画が得意**: 図鑑カードに駅名やキャラ名を焼き込む用途にも使える（任意）。

> ⚠ 要確認: 子供向け商用サービスでの利用規約・商用利用可否、レート制限、地域可用性は Google 公式規約で最終確認する（§12）。

## 4. 生成プロンプト設計

プロンプトは「固定部（ブランディング）」＋「旅の変数」＋「ユーザー変数」で構成する。**ユーザー由来の自由テキストは入れない**（安全・プロンプト混入対策）。

| ブロック | 中身 | 由来 |
|---|---|---|
| ブランディング固定部 | 画風・頭身・配色・線・「テクタン」の世界観・**子供向け安全指示**（怖すぎない/暴力・性的表現なし 等） | 固定＋参照画像 |
| 駅モチーフ | 駅名（＋その土地の特徴語） | アプリデータ（安全） |
| スポットモチーフ | 通ったスポット名/カテゴリ（史跡・自然・科学館 等） | Places 由来（**サニタイズして"テーマ"として渡す**） |
| 距離要素 | 距離帯 → レア度/風格（§6） | 計算値 |
| ユーザー変数 | 生き物タイプ×印象（§5） | メニュー選択（安全） |

- スポット名は外部（Places）由来のため、そのまま指示に混ぜず「モチーフのヒント」として渡し、画風はブランディング固定部で押さえる。
- 同一プロンプト＋seed違いで3体の差（シルエットの違い）を作る。

## 5. ユーザー変数 ＝ 生き物デザインの汎用記述語彙（[[archetype taxonomy]]）

### 5-1. 方針
- **狙い**: 男の子が好むかっこいい/怪獣系〜可愛い系まで、**自由度高く・でも安全**に選べること。
- **作り方**: ポケモン等の**1000体超の大規模ロスターを「言葉でどう表現されるか」を分析**し、そこから**IP非依存の汎用記述語彙**（体型・手足・付属物・質感・モチーフ・印象）を抽出してメニュー化する。
- **⚠ IP注意（最重要）**: 特定キャラの固有特徴・名称・意匠は**コピーしない**。抽出するのは「よつあし/つばさ/は虫類的」等の**一般的な形態記述**のみ。画風はうちのブランド（参照画像）に固定するため、出力は他社IPに寄らない。

### 5-2. メニュー構造（案: 2軸選択）
ユーザーは2つだけ選ぶ（子供が迷わない粒度）。組合せで多様性を確保。

- **軸A: からだのタイプ（body archetype、約10）**
  よつあし（けもの）/ とり・つばさ / は虫類・ドラゴン / むし / みずの生き物 / ちいさいけもの / ひとがた / しょくぶつ / きかい・いわ / ふしぎ（おばけ・スライム系）
- **軸B: いんしょう（impression、約5）**
  かわいい / かっこいい / ゆうかん / ミステリアス / おっとり

例: 「かっこいい × ドラゴン」「かわいい × とり」。10×5＝**50通り**で自由度と安全性を両立。

> 拡張余地: 語彙は後から増やせる。将来は軸C（モチーフ）を旅（駅・スポット）から自動付与し、ユーザー選択と自動要素を掛け合わせる。

### 5-3. 別案（不採用寄り）
- 自由入力: 却下（モデレーション＋プロンプト混入リスク）。
- 単一軸（動物だけ）: 自由度が足りず、男の子の「かっこいい」欲求を拾いにくい。

### 5-4. 実装状況（本番語彙DB統合済み・2026-07-12）
- ロスター分析による**本番語彙DB**（`docs/30-research/character-taxonomy/`）を作成し、アプリ組込用に `src/data/vocab.js` へ変換して統合。
- 6論点（[[タイプ]]／[[モチーフ]]／[[質感]]／[[表情]]／[[装飾]]／[[雰囲気]]）×`app_auto`（被りやすい＝アプリ自動）/`user_selectable`（被りにくい＝ユーザー個性）。
- **生成プロンプト**（`buildPrompt`）はこの6論点語彙で構成し、候補ごとに `makeVocabPicks()` を付与・保存（実API生成の主入力）。
- なお `src/data/archetypes.js`（からだ×いんしょうの短いラベル）は**UI層専用**（シルエット多様化・命名）として併存。プロンプトの主役は vocab、UI表示の主役は archetypes、と役割分担。
- ※現状は case Y（明示メニューなし）。`user_selectable` を明示メニュー化（case X）する場合は、この vocab をそのままメニューソースに使える。

## 6. 距離 ＝ レア度 ＋ 共有プールへの出現重み

距離（＝がんばり）を **レア度**にマッピングし、レア度が**共有キャラとして他人に出る確率**を決める。

- **距離帯 → レア度**（バケット例、境界は要決定）: コモン → レア → エピック → レジェンド。
- **見た目への反映**: レア度に応じたオーラ/フレーム/きらめき（既存 variant システムのフィルタ資産を流用可能）。
- **共有出現重み**: `出現重み = f(レア度, 距離)`。**距離が長い＝重みが大きい＝他ユーザーの探検で出やすい**。
  - 例: コモンは自分＋同駅の近縁のみ、レジェンドは路線全体で高頻度出現。
- **既存 variant との関係**: 生成キャラにもレア度（variant相当）を付与し、図鑑キー体系 `charId#variant` に整合させる。

## 7. 作成ステップ UX ＆ タイミング（先行生成）

### 7-1. タイミング設計（レイテンシ隠蔽）
生成には時間がかかるため、**ユーザーがレポート/スコアを見ている間に裏で先に作っておく**。

1. **[[探検おわり]]押下 → レポート生成の"前"に作成可否を判定**（§2ゲート）。
2. **可の場合は、その場で裏で3体の先行生成を開始**（[[バックグラウンド生成]]）。ユーザーには何も見せない（まだ作るとは限らないため）。
3. 続けて**レポート作成・スコア表示**（この間に生成が進む＝待ち時間を隠す）。
4. レポート/スコアを見せた**後**に「**あたらしいなかまを むかえる？**」と作成意思を確認。
5. **YES** の場合のみ、**裏で用意していた3体を §7-2 の流れで表出**させる。**NO** の場合は破棄（または「あとで」保留、要決定）。

> 先行生成は「作るかも」の投機実行。ユーザーが NO を選んだ場合の生成コストは無駄になるが、体験の滑らかさを優先する（コスト対策は§12。ゲートで頻度が絞られるため許容範囲）。

### 7-2. 表出フロー（YES 後）
1. 先行生成済みの**3体を灰色シルエットで提示**（色・細部は隠す＝開ける楽しみ）。
2. ユーザーが**1体を選択**。
3. 選んだ1体が**カラーで登場**（演出）。残り2体は**棄却**（「きえちゃった…」の軽い演出、データは破棄）。
4. **命名**（候補から選ぶ、§8）→ 図鑑に登録（§11）。レア度によっては共有プールへ（§10）。

> 演出上のポイント: シルエットは形（体型）で選ばせ、色・レア度は開けるまで隠す＝**ガチャの高揚感＋自分で選んだ愛着**。

### 7-3. ユーザー変数の投入タイミング（要決定）
先行生成は「作るか」を聞く前に走るため、**ユーザー変数（軸A×軸B, §5）をいつ選ばせるか**に選択肢がある:

- **案X（明示メニュー維持）**: ①の可否判定の直後（レポート前）に軽く軸A×Bを選ばせ、その変数で先行生成。最終的な「作る/やめる」は④で聞く。→ メニューの自由度を残せる。
- **案Y（ピックに統合）**: 変数は選ばせず、**3体を異なる archetype で先行生成**し、⑤のシルエット選択そのものを「変数の表明」とする。→ 事前入力ゼロで④の"後から聞く"と最も素直に噛み合う。
- **採用: 案X（実装済み・2026-07-12）**。探検おわり時に軽いティーザー「どんなのが すき？」で **モチーフ×ふんいき**（語彙DBの `user_selectable` プール）を選ばせ、その変数で裏の先行生成を開始。最終の「むかえる/やめる」はスコア表示後に確認。未選択軸は `app_auto` からランダム、「おまかせ」で全ランダム。3体はユーザー選択（motif/atmosphere）を共有し、他軸＋seed で差を出す。

## 8. 命名（候補から選ぶ）

- **安全な名前リスト**＋**駅名/変数を混ぜたテンプレ候補**を数個提示して選ばせる（自由入力は不採用＝子供向け安全）。
  - 例テンプレ: 「〇〇（駅）の△△」「△△っち」「ぷち△△」等。
- 自由入力を将来入れる場合は NGワード＋AIモデレーション必須（現段階は不採用）。

---

## 9. 乱造方針（探検ごとに1体）

- **条件を満たすたびに1体**新規生成（駅ごとの重複制限は設けない）。
- farm（乱造）の抑制は**§2のゲート（実行点＋実探検の証明）**が担う＝「歩かないと作れない」ので自然に頻度が制限される。
- コスト面は§12でレート・バッチ・上限で管理。

## 10. 共有キャラ（他人に出る）＝ モデレーション＆子供プライバシー設計

**他の子供に見せる**以上、ここが最重要。

### 10-1. プライバシー（子供保護）
- 共有プールに載せるのは **キャラ画像・駅・路線・レア度・匿名ハンドル（ニックネームのみ）** だけ。
- **作者の個人情報（本名・メール・位置履歴・スコア詳細）は一切ひも付けない**。
- 「自分のキャラを共有に出す」ことへの**保護者/本人の同意（オプトイン）**を検討（要決定）。

### 10-2. モデレーション（多層）
1. NanoBanana Pro の **IMAGE_SAFETY**（サーバ側・無効化不可）。
2. うちの**自動画像チェック**（不適切表現の二次分類）を共有プール投入前に実施。
3. **通報ボタン**＋必要に応じ**人手レビューキュー**（共有プール限定でよい）。
4. 入力が**限定メニュー＋データ由来**（自由入力なし）なので、そもそも危険入力の面は小さい。

### 10-3. 出現ロジック
- 共有プールは**路線/駅キー**で管理。他ユーザーの探検時、その路線の共有キャラを**レア度・距離由来の重み**で AR に動的注入（§6）。

## 11. データ設計・図鑑連携

- **画像**: Drive に保存（既存のセッション保存基盤を流用）。SynthID により来歴担保。
- **メタ**: Sheets に1行（`charId` / 駅 / 路線 / レア度 / 生成日時 / 匿名作者ハンドル / 変数(軸A,軸B) / 共有フラグ / モデレーション状態）。
- **charId 体系**: 生成キャラ用の名前空間（例 `gen_<路線>_<連番>` 等）を新設。図鑑キーは既存の `charId#variant` に整合（レア度＝variant相当）。
- **図鑑**: 既存のコンプ枠に**動的注入**。生成キャラも「すがた（variant）」やレア度表示に乗る。
- **GAS**: 保存/取得アクション追加（**再デプロイ必要**）。既存 `captures`/`users` と同様のパターン。

## 12. コスト・レート・失敗時フォールバック

- **コスト目安**: 1体作成＝1リクエストで最大4枚。標準ルートで概ね1枚 $0.13 前後（2K）、バッチで $0.07 前後（第三者情報のため要最終確認）。3候補で概ね**$0.2〜0.4/作成**。
- **抑制**: §2ゲートで頻度が自然に制限される＋**全体の1日あたり生成上限＝24枚/日（≒8回/日）をサーバー側（GAS `generateCharacters` / `gen_guard` シート）で実装済み**。これで**月額 ¥30,000 以下を保証**（$0.24/枚・$1=¥162・31日の保守前提で ≒¥29,016）。上限は定数 `GEN_DAILY_IMAGE_LIMIT` で一元管理。到達時は `daily-limit` を返しフロントはモックへフォールバック。**1ユーザー単位**の上限は必要時に `userId` を渡して追加（要決定のまま）。可能なら**バッチAPI**でコスト削減。**スタイル参照画像はキャッシュ**。
- **失敗/ブロック時フォールバック**: `IMAGE_SAFETY`・生成失敗時は**自動リトライ1回** → なお失敗なら**用意した安全なテンプレキャラ**を付与し、**お祝いの瞬間に"失敗"を出さない**。
- **規約確認（要）**: 子供向け商用利用の可否、地域可用性、レート上限を Google 公式で確認。
