## 1.5 ソースコードを外部に見せない選択肢とコスト（2026-07-13 追加）

### 大前提（重要）：クライアントJSは"完全には隠せない"

ブラウザで動くアプリのJS/HTML/CSSは**必ず利用者の端末に配信される**ため、DevToolsを開けば誰でも読める。「配信されるコードを100%隠す」ことは技術的に不可能。現実的な"秘匿"は次の3層で考える：

1. **リポジトリ非公開**＝整理された全ソースツリー・コメント・コミット履歴・設定を見せない（← 今回の主目的。これは無料で達成可能）
2. **配信JSの minify / 難読化**＝DevToolsで読まれても解読しにくくする（[[esbuild]]/[[terser]]＋[[javascript-obfuscator]]。ビルド1工程・無料。ただし決定的な保護ではない）
3. **重要ロジック・秘密をサーバ側へ**＝キャラ生成プロンプト／語彙DB／採点ロジック等"見られたくない核"を [[GAS]]/[[Cloudflare Workers]] に置き、ブラウザに送らない（＝Plan B の本質。唯一の本格的な秘匿）

> **GitHub Pages 固有の制約**：Private リポジトリからの Pages 公開は **GitHub Pro（$4/月 ≒ ¥600/月）以上が必要**。だが**この制約は GitHub Pages だけの話**で、下記の他ホスティングは**非公開リポジトリ（またはビルド済みファイルの直アップロード）から無料で公開でき、レイヤー1は¥0で達成できる**。

### 本アプリ規模での試算

自ホストが配信するのは**静的バンドル（JS/CSS/HTML ≒ 数百KB／初回ロード、以降ブラウザキャッシュ）だけ**。地図タイル・生成キャラ画像・写真は Google Maps／Gemini／Drive 側から配信され、**自ホストの帯域を消費しない**。したがって：

- **月数千セッションでも自ホスト帯域は概ね 1GB/月 未満**に収まる見込み。
- → 上表のどの無料枠（最小の Firebase 10GB/月 でも）でも**コストは実質 ¥0**。帯域が理由で有料化する状況は当面来ない。

### 推奨

- **「リポジトリを隠したいが無料で」** → **Netlify** か **GitLab Pages** に**非公開リポジトリから公開**が最短（既存の静的構成のまま、公開先を差し替えるだけ）。
- **「ビルド済みだけ置いてリポジトリすら渡したくない」** → **Firebase Hosting（CLIデプロイ）** か **S3+CloudFront**。
- **現行 GitHub Pages を動かしたくない** なら **GitHub Pro ¥600/月** が最小の追加コスト（上表の無料手段に移せば¥0）。
- ⚠️ **どれを選んでもレイヤー1（リポジトリ秘匿）止まり**。配信JS自体は読める。**キャラ生成プロンプト等"本当に見られたくない核"は、難読化（レイヤー2）＋サーバ寄せ（レイヤー3＝Plan B）でしか守れない**。まず無料でレイヤー1、本気の秘匿が要るなら Plan B と同時に③をやる、という順序が費用対効果が高い。

### ✅ 採用：Netlify への移行（2026-07-13・設定ファイル作成済み）

push→自動デプロイの快適さを残したまま、リポジトリを Private 化してソースを隠す方式を採用。**リポジトリ直下に `netlify.toml` と `netlify-build.sh` を追加済み**。

- **公開されるのは実行ファイルだけ**：ビルドで `dist/`（`index.html`・`policy.html`・`404.html`・`src/`・生成した `config.js`）だけを配信。**`gas/`・`docs/`・`config.example.js`・`test-gen.html`・`variant-preview.html` は配信されない**（GitHub Pages 時代は全ファイルが公開されており、特に `test-gen.html`＝課金生成を誰でも叩けた点が改善）。
- `config.js` は Netlify の環境変数から生成（GitHub Actions と同等）。`?v=` は `COMMIT_REF`（コミットSHA）でスタンプ。

**移行手順（ユーザー操作）**：
1. [app.netlify.com](https://app.netlify.com) でアカウント作成 → **Add new site → Import an existing project → GitHub** を選び、**（Private のままの）`tanken-rally` リポジトリ**を連携。
2. Build 設定：`netlify.toml` を自動検出（command=`bash netlify-build.sh`／publish=`dist`）。手動なら同値を入力。
3. **Environment variables** に3つ登録：`GOOGLE_MAPS_API_KEY`・`GAS_URL`・`GAS_SECRET`（GitHub Secrets と同値）。
4. **Branch deploys** で `beta` を有効化 → `beta--<site>.netlify.app` がプレビューになる（旧 `/beta/` サブパスの代わり。相対パスなので改修不要）。
5. ⚠️ **Google Maps APIキーの HTTP リファラー制限に Netlify ドメインを追加**：`https://<site>.netlify.app/*` と `https://beta--<site>.netlify.app/*`（独自ドメイン利用時はそれも）。**やらないと地図が真っ白になる**。旧 `github.io` は残置でも可。
6. デプロイ確認（地図・写真アップロード・PDF・キャラ生成が通るか）。OKなら **GitHub リポジトリを Private 化**し、`.github/workflows/deploy.yml` は不要になるので削除（Private だと Pages ビルドが失敗して紛らわしいため）。
7. （任意）独自ドメインを Netlify に接続。その場合はリファラー制限もそのドメインに更新。

> **これはレイヤー1のみ**：上記でリポジトリと `gas/`・`test-gen.html` は隠れるが、配信される `src/*.js` は依然ブラウザで読める。核ロジックの秘匿が必要になったら Plan B（難読化＋サーバ寄せ）へ。

### 3.3 含意と打ち手

- **損益ライン**: 顧客単価（広告/課金/スポンサー）が **¥100/月・人** を超えないと変動費で赤字。無料アプリのまま伸ばすと月1,000セッションで¥4万超の持ち出し
- **コスト削減の優先順位（効果順）**
  1. **駅単位キャッシュ**: 人気駅に集中するため Places コールを 80〜90% 削減見込み → **2026-07-08 実装済（§3.4。GAS/Sheets、TTL 1年）**
  2. **検索キーワードの削減/段階化**: 14キーワード一括 → 主要5つ先行+ユーザー要求時に追加取得で単価半減
  3. Places API (New) への移行: Text Search Essentials（IDs only）は無料枠が別建て。フィールドマスク設計次第で大幅減
  4. 営業時間取得（getDetails）を選択スポットのみに限定（現状に近いが上限を明示）
- **課金上限の防波堤**: 日次クォータ上限を「想定セッション数×15」に設定しておけば、**最悪月額はクォータで機械的に頭打ち**にできる（リスク#3対策と同一）

### 3.4 【2026-07-08 実装済】駅スポットの[[キャッシュDB]]（GAS/Sheets）

上記「打ち手1」を実装した。Drive（Sheets）上の `spots_cache` タブを駅情報 DB とし、既知の駅は [[Places API]] を呼ばずに再利用する。

- **仕組み**: 駅の検索結果（スポット一覧 JSON）を キー = `スキーマ版|言語|駅座標(小数4桁)` で Sheets に upsert。ヒット時は Places 検索（Nearby ×14 + Text ×1）を丸ごとスキップ
- **TTL = 365日**（[[GAS]] 側 `SPOTS_CACHE_TTL_DAYS`）。1年経過した駅は自動的に miss 扱い → 再検索して同じ行を上書き（＝1年ごとに情報更新）
- 変更ファイル: `gas/Code.gs`（`getSpotsCache` / `saveSpotsCache`）、`src/utils/drive.js`、`src/main.js`
- **反映には GAS の再デプロイが必要**（script.google.com で Code.gs を更新 → 「デプロイ」→「デプロイを管理」→ 既存デプロイを編集して新バージョンで再デプロイ。URL を変えないため config.js/Secrets の変更は不要）
- **⚠️ 規約リスク（リスク#10 の具体化）**: Google Maps Platform ToS では Places コンテンツのキャッシュは原則30日以内（`place_id` のみ無期限保存可）。**TTL 365日は規約違反となる可能性がある**。回避策: (a) TTL を30日に短縮する、(b) 保存項目を place_id + 自前加工データに限定する構成へ改める、(c) リスク受容のまま運用。現状は (c) で、`SPOTS_CACHE_TTL_DAYS` を変えるだけで (a) に移行できる

**キャッシュヒット率 80%（利用が人気駅に集中する前提・ウォームアップ後）の推定月額:**

| 月間セッション数 | キャッシュなし | キャッシュあり(80%) | 削減率 |
|---|---|---|---|
| 1,000 | 約 ¥4.3万 | **≒ ¥0**（無料枠内） | 100% |
| 3,000 | 約 ¥20万 | 約 ¥3.4万 | 83% |
| 10,000 | 約 ¥75万 | 約 ¥22万 | 71% |

※ 大規模時は営業時間取得（Place Details、日時フィルタ使用時のみ発生）が次の支配項になる。次の最適化候補は opening_hours もキャッシュ対象に含めること。
※ 無料枠内で収まるラインは 月357セッション → **約1,780セッション**（ヒット率80%時）に拡大。

### 3.5 [[Google Drive]] / GAS / Sheets のコスト

これまで「無料」と一括りにしていた部分の内訳。**基本は¥0だが、上限（クォータ）がコストの代わりに効いてくる**。

| 項目 | 無料枠 | 超過時 | 本アプリでの見通し |
|---|---|---|---|
| Drive ストレージ | **15GB**（Gmail・フォトと共用） | [[Google One]] 100GB **¥290/月**、2TB ¥1,450/月 | 写真は30日で自動削除。定常在庫 ≒ 日次セッション数 × 写真5枚 × 3MB × 30日 ＝ 日次セッション数 × 約450MB。**日33セッションで約15GB（無料枠上限）に到達**。日30セッション前後で100GBプラン（¥290/月・約220セッション/日まで）、日200セッション超で2TB（¥1,450/月）推奨 |
| spots_cache（Sheets） | 同上 | 同上 | 1駅 ≒ 10KB。全国9,000駅 × 3言語でも約270MB。**実質無視できる** |
| Sheets セル数上限 | 1,000万セル/ファイル | 分割が必要 | cache は1駅1行（6セル）。ランキング/ログ行が先に効くが当面問題なし |
| GAS 実行 | 同時実行30、1実行6分、トリガー計90分/日 | 増枠不可（Workspace 移行で緩和） | 写真アップロード集中時に同時実行30が最初のボトルネック。**キャッシュ導入で GAS 呼び出しは +2回/セッション増える**が軽量（数百ms）で影響小 |
| GAS URL Fetch 等 | 2万回/日 ほか | 増枠不可 | 現状未使用（OpenAI プロキシ化すると消費し始める点に注意） |

**結論**: 顧客数との関係で言うと、Drive 起因の支出は「日次セッション数 ×写真枚数 ×保持30日」で決まり、**月¥0 →（日33セッション超で）¥290/月 → （日220セッション超で）¥1,450/月** と階段状に増える程度。API 課金と比べ1〜2桁小さく、意思決定には効かない。ただし **保持を7日→30日にしたぶん定常在庫が約4.3倍になり、無料枠15GB に当たるのが「日33セッション」と早い**点に注意。**15GB 超過で写真アップロードが全停止する**ため、「Drive 使用量が80%を超えたらアラート」を運用チェックリストに入れること（リスク#4/#9 とも連動）。

**🆕 生成キャラ画像は別枠**：`_generated_characters` フォルダに保存する生成キャラ画像は**30日削除の対象外＝恒久保存**。1枚 ≒ 0.3〜1MB。生成が増えるほど Drive を食い続けるので、写真とは別に「生成キャラの総容量」も監視対象に。将来は古い/未使用の生成画像の間引き or 外部ストレージ移行を検討。

### 3.6 【2026-07-12 追加】[[キャラ自動生成]]（[[Gemini画像生成]]）のコスト ＝ 新しい支配項

これまでの最大コストは Places だったが、**キャラ自動生成が発生するセッションでは Gemini 画像生成がそれを上回る**。

- **単価**: `gemini-3-pro-image` で **約 $0.13〜0.24/枚**、**1体生成＝3枚**なので **≒ $0.4〜0.7/生成**（≒¥60〜105）。無料枠なし。※Google の最新料金で要確認。
- **発生頻度の制御（実装済）**: 生成は「一定以上歩く＋写真を撮る」eligibility ゲートを通過した探検で**1探検につき1回だけ**（`consumed` フラグを session に永続化）。＝**全セッションでは起きない**。
- **未実装の要対策**: **1ユーザー1日あたりの生成上限**（コストの物理天井）。上限が無い現状は、悪意ある連打で高額化しうる（リスク#11）。安全性（不適切生成）は**帰納的検証方式**で担保する方針（常時モデレーションは実装しない・§1-5 / リスク#11 参照）。

**「生成率」別の追加月額の目安**（生成率＝全セッション中キャラ生成が起きる割合。1生成=$0.55≒¥83 と仮定）:

| 月間セッション | 生成率10% | 生成率30% | 生成率50% |
|---|---|---|---|
| 1,000 | 約 ¥8,300 | 約 ¥2.5万 | 約 ¥4.1万 |
| 3,000 | 約 ¥2.5万 | 約 ¥7.5万 | 約 ¥12万 |
| 10,000 | 約 ¥8.3万 | 約 ¥25万 | 約 ¥41万 |

- **含意**: Maps は駅キャッシュで抑えられるが、**Gemini生成はキャッシュが効かない純増コスト**。生成率が高いと、Maps を上回る最大の変動費になる。
- **打ち手（効果順）**:
  1. **1日あたり生成上限**（例: 1ユーザー3回/日、全体N回/日）＝機械的な天井。最優先。
  2. **下書きは `gemini-2.5-flash-image`（約$0.04/枚）**に切替＝単価を1/3〜1/5に。最終採用時のみ pro に。
  3. 生成トリガーをさらに絞る（レジェンド等の特別枠のみ生成、通常はモック等）。
  4. GCP（Gemini）側にも**別の予算アラート/上限**を設定（Maps とは課金プロジェクトが別なら特に）。
